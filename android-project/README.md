# PrintShop Customer Manager

A native Kotlin Android application using Jetpack Compose, Material 3, MVVM, Firebase Authentication, and Cloud Firestore.

## Features

- Email/password staff registration, sign-in, password reset, and sign-out.
- Auth-gated dashboard with a live Firestore customer count.
- Create, list, search (name, phone, and email), view, edit, and delete customer profiles.
- Form validation and an Android date picker for date of birth.
- Live customer updates, loading/error/empty states, and retryable user-facing errors.
- An idempotent demo-data action that adds up to 10 synthetic customer records.
- Firestore rules that require authentication and validate document shape.

## Open and build in Android Studio

1. Install Android Studio with Android SDK Platform 35 and a Java 17 JDK.
2. Open this project folder (`PrintShopCustomerManager`) in Android Studio and allow Gradle sync.
3. Configure Firebase using the steps below.
4. Select an Android emulator with API 26 or newer, then run the `app` configuration.
5. To build an APK, use **Build > Build Bundle(s) / APK(s) > Build APK(s)**. The debug APK is written under `app/build/outputs/apk/debug/`.

The Gradle wrapper is not included in this source folder. Install/configure Gradle 8.9 with Android Studio, or generate a wrapper from the project root using `gradle wrapper --gradle-version 8.9`. Then run `gradle :app:testDebugUnitTest` and `gradle :app:assembleDebug` (or use the generated `gradlew.bat`).

## Firebase setup

Firebase is a required external service. No Firebase project or application credentials are bundled with this source.

1. Create a Firebase project in the Firebase console.
2. Add an Android app with package name **`com.printcare.app`** and download its `google-services.json`.
3. Place that file at **`app/google-services.json`**. It is intentionally excluded from Git by `.gitignore`.
4. In Firebase Authentication, enable the **Email/Password** provider.
5. Create a Cloud Firestore database, then deploy this project's rules from the project root:

   ```text
   firebase deploy --only firestore:rules
   ```

   The included `firebase.json` points the Firebase CLI at `firestore.rules`. Select your Firebase project in the CLI with `firebase use --add` first.
6. Sync Gradle and run the app. Without Firebase configuration the app still builds and shows an explicit setup message instead of crashing; authentication and cloud data operations require the configuration above.

The Google Services Gradle plugin is applied only when `app/google-services.json` exists. Never commit service-account private keys, signing keys, or passwords. The Android Firebase configuration contains client identifiers; Firestore rules and Firebase Authentication must protect data, not secrecy of the client config.

### Firestore data shape

Collection: `customers`. Document IDs are generated by Firestore (seed documents use stable `demo_customer_01` … `demo_customer_10` IDs).

| Field | Type |
| --- | --- |
| `customerId` | string; equals the document ID |
| `fullName` | string |
| `phoneNumber` | string; 10-digit Indian mobile |
| `dateOfBirth` | string; `DD/MM/YYYY` |
| `email` | string |
| `address` | string |
| `createdAt` | Firestore timestamp |

Older PrintCare documents using `name`, `phone`, and `dob` remain readable. Saving an older record replaces it with the current field names while preserving its existing registration timestamp.

### Demo data

Sign in, open the dashboard, and choose **Add fictional demo data**. The app writes ten fictional records using `.invalid` email addresses and fixed demo document IDs. Repeating the action skips records already present. The sample phone numbers are synthetic test values; do not use this dataset for contacting people or as production customer data.

## Security rules and limitations

The rules deny all unauthenticated customer access and validate required fields and basic value shapes. Any Firebase-authenticated account can currently read, create, update, and delete every customer. Sign-up is available in the app, so this is appropriate only for a controlled demo or trusted staff deployment. For production, restrict account creation and enforce shop membership/roles with verified custom claims or a trusted backend; UI hiding is not authorization. The rules' date check validates the string shape but cannot reliably reject every impossible calendar date. Client-side validation is for usability, not a security boundary.

## Tests and verification

Local unit tests cover email/phone/name/address validation, leap-day and impossible dates, and future DOB rejection:


The project also needs Android SDK Platform 35, Gradle/Android Studio, Java 17, Firebase configuration, and an emulator or device to run the full integration checklist.
